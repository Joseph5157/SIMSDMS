# 030-H — Spec 031 Decision Inputs

This is an evidence package for **031 — UI Architecture & Design-System Decision**. It presents current facts and constraints only. It does not choose a library, component architecture, migration sequence, or visual target.

| Decision topic | Current evidence | Constraints / evidence to preserve | Questions Spec 031 must answer |
| --- | --- | --- | --- |
| Mantine scope | Mantine Core has 34 importing files and owns theme/provider, shell, controls, overlays, table internals, and layout primitives. Mantine Hooks are localized. | Any change has broad shell/form/action/table/theme impact; preserve accessible behavior and dark-mode readability. | Should Mantine remain at current scope, be reduced, or receive a more explicit direct-use boundary? |
| Direct versus wrapped primitives | AppButton 1 consumer; AppSelect 7; AppTextInput 2; AppNumberInput 0; direct Mantine/native/raw paths are broad. Some wrappers add material behavior, others do not. | Do not misclassify composite, navigation, calendar, pagination, search, auth/file/time/date, or shared sheet-footer controls as generic CTA duplication. | Which wrappers, if any, are canonical? What direct/native exceptions are sanctioned? |
| Actions/buttons | 70 direct Mantine Buttons, 82 raw buttons, 32 closest conventional-action raw overlaps; global Mantine theme already provides a 44px floor for Mantine Buttons. | Preserve meaningful raw composite/shell semantics and current success/feature variants until policy exists. | Should AppButton expand, remain limited, or be superseded? How should naming/loading/target rules be enforced? |
| Forms | AppSelect’s non-portal default is materially useful in Radix overlays. Native controls serve search/auth/file/time/date/report contexts; visual differences are generally subtle. | Do not assert all fields currently use a wrapper. Preserve labels, keyboard/combobox behavior, and overlay portal safety. | What is the field ownership model and which native controls are deliberately retained? |
| Overlay architecture | ResponsiveSheet 10, FormModal 8, ConfirmDialog 12, direct Mantine Modals 2, shell Drawer, Menus; bounded StudentSearchOverlay Radix/Framer exception. FormModal/ConfirmDialog focus return failed in tested paths. | Preserve working sheet mobile/keyboard/safe-area/drag responsibilities; do not copy the nested exception casually; address focus with behavioral tests. | Which task belongs to each overlay contract? Does StudentSearchOverlay remain an exception? What focus-return expectation is required? |
| Tables and responsive data | Shared Table is broad (27/12 files); ResponsiveDataView/MobileList one consumer; seven local mobile-card/table pairs; 767/768 works on four tested pages. Reports secondary mobile tables clip. | Preserve table semantics, density, status language, and proven 767/768 behavior. Do not assume every table should become a card. | Should ResponsiveDataView expand, be replaced, or remain narrow? Which data types use cards, tables, or intentional horizontal scroll? |
| Tokens and theme | Tailwind `@theme`, CSS semantic/dark variables, Mantine arrays (72 hex literals), and local styles coexist. Theme screenshots are readable. | A token change must preserve light/dark semantics and avoid breaking Mantine consumers; current manual synchronization is a real risk. | What owns semantic values, library adapters, and dark mode? How should duplication/synchronization be governed? |
| Dependencies with no direct app use | Mantine Notifications and Geist have zero direct production imports; Recharts is a Mantine Charts peer/runtime, not a direct source API; `cn()` has no downstream use. | Zero source imports do not prove safe removal; avoid package changes before architecture and runtime/build implications are decided. | Retain, remove, or repurpose which packages/utilities, and with what validation? |
| Charts | One page directly uses Mantine Charts (one line, two bars); no chart wrapper/direct Recharts imports. | Preserve current analytics display and peer dependency relationship. | Is an application chart boundary useful for one current consumer? |
| State/feedback | Custom Toast is active (100 calls/25 consumers); Alert is inline; table states are shared; non-table loading/empty/error patterns are uneven and valid forced state captures were incomplete. | Do not replace the active Toast path accidentally; distinguish semantically different loading/empty/error/offline cases. | What state-pattern policy is needed, and how should it be tested? |
| Breakpoint governance | Shell/dominant data switch: 767/768. ResponsiveSheet/StudentSearchOverlay/Reports: 639/640. FormModal: 640/641. | These are browser-confirmed current facts, not necessarily target tokens. Preserve working transitions while deciding terminology/ownership. | What breakpoint vocabulary/source of truth should govern shell, content, and overlay behavior? |
| Accessibility | No nameless visible interactive elements in 58 captures; focus return varies; some visible Reports targets are 37–40px; nested dialog behavior works one Escape level. | Preserve semantic shared Table/overlay behavior, safe areas, keyboard behavior, role access, and dark-mode readability. | What requirements deserve lint/test enforcement, and how will regressions be verified? |
| Visual language | Operational shell/type/status identity is coherent. Dashboards are Level 2 generic-pattern accumulation; Reports is Level 3 with 15 emoji/colour cards and dense mobile composition; no Level 4 captured. | Preserve operational density, meaningful status color, Faculty duty priority, and restrained pages as counter-evidence. Do not turn aesthetic observations into blanket bans. | What visual priority, gradient, card, icon/emoji, motion, and report-discovery policy should govern future work? |
| Browser-confirmed defects | Reports mobile clipping, Admin invalid nesting/hydration warning, focus-return inconsistencies, and selected target-size concerns are confirmed. | Keep defect evidence separate from aesthetic preferences and select fixes only after architecture decisions. | Which fix sequence and verification criteria are appropriate? |
| Testing | Original E2E was sparse; 030-D created strong audit coverage (58 captures/34 interactions/82 screenshots) but has no client unit baseline and known harness gaps. | Treat screenshots/raw results as baseline evidence; do not treat unverified paths as failures. | What durable client, browser, a11y, visual, and seeded-state coverage is required before migration? |
| Agent governance | 030-G reconciled active docs/skills to current Public Sans, Tabler, auth, overlays, feedback, and responsive facts. | Keep historical prototype assets bounded; no future policy should be presented as current until approved. | What new decisions must be reflected in Constitution/CLAUDE/UI Architecture/Mobile Patterns/skill guidance? |
| 21st.dev / external components | No evaluation, research, selection, or installation occurred in Spec 030. | Do not import a new icon system, token model, primitive architecture, or visual language by default. | Is it appropriate at all?
